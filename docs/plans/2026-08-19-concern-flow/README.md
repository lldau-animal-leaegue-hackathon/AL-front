## Context

지금 앱은 **제품에서 출발**한다. 제품을 담고(스캔) → 루틴을 만들고 → 수행한다.
사용자 요청은 축을 **고민에서 출발**하는 쪽으로 옮기는 것이다:

> 고민 등록 → 그 고민에 효과 있는 **성분 추천** → 그 성분이 든 **제품 추천** →
> 선반에 담기 → **루틴 생성으로**

지금은 고민(`SkinProfile.wonder`)이 루틴 생성 폼 안에서 한 번 입력되고 프로필에 표시만 된다.
고민을 **입구**로 올리면 "무엇을 사야 하는지 모르겠다"는 상태에서 앱을 시작할 수 있다.

### 요청 정리 (2026-08-19)

| #   | 요청                                                         | 다루는 절          |
| --- | ------------------------------------------------------------ | ------------------ |
| 1   | 바텀탭에서 **루틴↔프로필 위치 교체**, 프로필 → **"내 고민"** | Q1 · Step 1        |
| 2   | 내 고민 탭: 고민 등록 → 성분 추천 → 제품 추천 → 선반 담기    | Q3 · Q4 · Step 3~4 |
| 3   | 거기서 **루틴 생성하기로** 이어짐                            | Step 5             |
| 4   | 루틴을 **기본 루틴 / 고민 집중 케어**로 분화                 | Q5 · Step 5        |
| 5   | 인기제품 카드 클릭 → **성분·썸네일 모달 + 선반 추가**        | Q2 · Step 2        |
| 6   | 카드 디자인 통일                                             | Step 2             |
| 7   | 홈·스캔은 현행 유지                                          | —                  |

### 현재 구조 실측 (2026-08-19)

| 탭                | 내용                                                |
| ----------------- | --------------------------------------------------- |
| 홈 `/`            | 시계 · 달성률 · 스캔 카드 · 다음 단계 · 성분 알림   |
| 스캔 `/scan`      | 등록 폼(검색→후보→성분→등록) · 인기 제품 목록       |
| 루틴 `/routine`   | 주간 스트립 · 루틴 목록(카드 펼침) → 생성/수행/완료 |
| 프로필 `/profile` | 피부 프로필 · AI 분석 리포트 · 내 선반 · 기록       |

**이미 있는 것 — 새로 만들지 않아도 되는 것들:**

- `Routine.condition`(`"평소"`·`"생리 기간"` 등)이 **모델에 이미 있다.** "고민 집중 케어"는
  새 테이블이 아니라 이 필드로 표현된다(skincare-core 의 db9eaed 머지분).
- 루틴 생성 프롬프트는 `wonder`(고민)를 입력으로 받는다. 조건을 붙여 재호출하면 확장된다고
  skincare-core 계획서가 이미 적어 뒀다.
- 후보 검색(`/api/ai/search`)이 **화해 웹 검색 + 이미지**까지 동작한다. 제품 추천에 재사용할 수 있다.

**⚠️ 없는 것 — 요청 5번의 전제가 깨진다:**

`src/app/scan/products.ts` 의 인기제품 시드 24종은 이렇게 생겼다:

```text
{ id, name, brand, price, category }
```

**성분도 썸네일도 없다.** 요청은 "저장된 성분과 썸네일을 모달로"인데 저장된 것이 없다.
게다가 `price` 는 목업 값이다 — 화해 실측(2026-08-18)에서 가격은 재현되지 않아
**표시하지 않기로 이미 결정**했는데, 이 시드에는 남아 있다.

### scan-search 계획서와의 관계

[스캔 탭 디벨롭](../2026-08-18-scan-search/README.md)에 이미 있는 항목과 겹친다:

| scan-search 항목                    | 이 문서에서                               |
| ----------------------------------- | ----------------------------------------- |
| 상단 탭(스캔/선반/인기 제품)        | Q1 에서 **재검토** — 선반 위치가 달라진다 |
| 프로필의 내 선반 → 스캔 탭으로 이동 | Q1                                        |
| 인기 제품 탭 + 선반에 담기          | Q2 · Step 2                               |
| 하단바 5개 → 4개 유지               | 유지(이 문서도 4개)                       |

→ **이 문서가 scan-search 의 Step 2·5 를 흡수한다.** 그쪽은 검색 부분만 남긴다.

## 결정 필요 사항

### Q1. 프로필에 있던 4개 섹션을 어디로 보내나

프로필이 "내 고민"이 되면 성격이 바뀐다. 지금 있는 것들의 자리를 정해야 한다.

| 섹션           | 성격                                     |
| -------------- | ---------------------------------------- |
| 피부 프로필    | 고민·가용 시간 — **새 탭의 입구가 된다** |
| AI 분석 리포트 | 등록 제품의 성분 집계                    |
| 내 선반        | 등록 제품 목록                           |
| 기록           | 수행 이력                                |

- **옵션 A: 선반·리포트는 스캔 탭으로, 기록은 루틴 탭으로**
  scan-search 계획서의 "선반 서브탭" 결정과 맞물린다. 기록은 루틴 수행의 결과라 루틴 탭이 자연스럽다.
  - 장점: 각 탭이 한 가지 일만 한다. 내 고민 탭이 고민에만 집중한다.
  - 단점: 탭 2개가 서브탭을 갖게 돼 구조가 한 겹 깊어진다.
- **옵션 B: 내 고민 탭 하단에 그대로 남긴다**
  - 장점: 이동이 없어 변경이 가장 작다.
  - 단점: "내 고민" 탭이 예전 프로필 그대로가 된다. 이름만 바뀐 셈이라 요청 의도와 멀다.
- **옵션 C: 선반만 스캔으로, 리포트·기록은 내 고민 탭 아래에**
  - 장점: 선반은 "담는 곳(스캔)" 옆이 맞다. 리포트는 내 성분 현황이라 고민과 이어진다.
  - 단점: 기록이 고민 탭에 있는 게 어색하다.
- **추천: A.** 요청의 핵심이 "내 고민 탭의 메인은 고민 등록 → 성분 → 제품 → 루틴"이다.
  다른 것이 섞이면 그 흐름이 묻힌다.

### Q2. 인기제품 카드의 성분·썸네일을 어디서 얻나

시드에 없다(위 실측). 셋 중 하나를 골라야 한다.

- **옵션 A: 카드를 누르면 그때 AI 로 조회한다**
  기존 `/api/ai/search` + `/api/ai/ingredients` 경로를 그대로 탄다.
  - 장점: 새 데이터가 필요 없다. 이미 동작하는 경로다. 성분 근거가 실제 검색이다.
  - 단점: **누를 때마다 14~54초.** 모달을 열자마자 기다려야 한다.
- **옵션 B: 시드 24종에 성분·이미지를 미리 채워 커밋한다**
  한 번 AI 로 만들어 파일에 박아 둔다.
  - 장점: 카드 클릭이 **즉시** 열린다. 데모에서 가장 빠르다.
  - 단점: 24종 × 성분을 사람이 검수해야 한다(안 하면 지어낸 값이 고정된다).
    제품이 리뉴얼되면 낡는다.
- **옵션 C: 인기제품을 시드가 아니라 서버 카탈로그에서 가져온다**
  `products` 테이블은 **전체 공유 카탈로그**다. 누군가 담은 제품이 쌓인다.
  담긴 횟수 순으로 "인기 제품"을 만들면 성분·썸네일이 이미 있다.
  - 장점: 데이터가 실제 사용에서 나온다. 성분·이미지가 이미 저장돼 있어 **즉시** 열린다.
    "쓸수록 좋아지는 카탈로그"라는 서버 저장소 결정의 목적과 정확히 맞는다.
  - 단점: **초기에 비어 있다.** 아무도 담지 않으면 인기 제품이 0개다.
- **추천: C + B 폴백.** 서버 카탈로그를 우선 쓰고, 비어 있으면 시드를 보여 준다.
  다만 시드에 성분이 없으므로 **시드 카드는 눌러도 성분이 없다**는 점을 어떻게 다룰지가 남는다
  (A 로 그때 조회하거나, 시드에 성분을 채우거나).

### Q3. 고민 → 성분 추천을 어떻게 만드나

새 AI 호출이 필요하다. 출력은 "이 고민에 효과 있는 성분 목록 + 왜"다.

- **옵션 A: 도구 없이 모델 지식으로**
  - 장점: 빠르다(실측상 도구 없는 호출은 10~30초). 성분-효능은 **잘 알려진 지식**이라
    웹 검색 없이도 신뢰도가 비교적 높다.
  - 단점: 근거 출처가 없다. 이 레포는 "지어내지 않는다"를 지켜 왔다.
- **옵션 B: 웹 검색을 켠다**
  - 장점: 근거가 생긴다.
  - 단점: 40초+. 성분-효능은 특정 페이지를 인용하기 애매해 검색이 오히려 산만해질 수 있다.
- **추천: A**, 단 **"의학적 조언이 아니다"** 문구를 화면에 고정하고, 프롬프트에
  "확신이 없으면 넣지 말 것"을 규칙으로 박는다(기존 프롬프트들과 같은 규율).

### Q4. 성분 → 제품 추천을 어떻게 만드나

- **옵션 A: 기존 후보 검색(`/api/ai/search`)에 성분 검색어를 넣는다**
  "판테놀 세럼" 같은 질의를 만들어 화해에서 찾는다.
  - 장점: 새 엔드포인트가 없다. 이미 이미지·브랜드까지 나온다.
  - 단점: ⚠️ **성분명 검색이 화해에서 되는지 미확인이다** — scan-search 계획서가
    "Step 3 착수 전 1회 측정"으로 남겨 둔 항목이다. **먼저 실측해야 한다.**
- **옵션 B: 서버 카탈로그에서 성분으로 거른다**
  `products.ingredients` 는 JSON 이라 검색 가능하다.
  - 장점: 즉시. 외부 호출 0. 이미 성분·이미지가 있다.
  - 단점: 카탈로그에 있는 제품만 추천된다(초기엔 거의 비어 있다).
- **추천: B 우선 + A 보완.** 카탈로그에서 먼저 찾고, 결과가 적으면 웹 검색으로 넓힌다.
  단 A 를 쓰려면 **성분명 검색 실측이 선행**이다.

### Q5. "고민 집중 케어" 루틴을 어떻게 만드나

`Routine.condition` 이 이미 있다("평소"·"생리 기간").

- **옵션 A: 생성 시 고민을 `condition` 에 넣는다**
  기본 루틴은 `condition: "평소"`, 고민 루틴은 `condition: <고민>`(예: "모공 집중").
  프롬프트는 그대로 두고 `wonder` 에 고민을 실어 재호출한다(skincare-core 가 예고한 경로).
  - 장점: 모델·프롬프트 변경이 0 이다. 루틴 목록만 그룹으로 나누면 된다.
  - 단점: 루틴이 여러 벌 쌓인다(아침·저녁 × 조건 수). 저장은 **통째 교체**라 구조를 바꿔야 한다.
- **옵션 B: 새 필드(`kind: "basic" | "focus"`)를 추가한다**
  - 장점: 의미가 명확하다.
  - 단점: 002 마이그레이션 + 모델 변경. `condition` 과 역할이 겹친다.
- **추천: A.** 이미 있는 필드로 표현되고, 계획서가 예고한 확장 경로 그대로다.
  ⚠️ 다만 **`saveRoutines` 가 사용자의 루틴을 전부 지우고 다시 넣는다** —
  기본 루틴을 만들면 고민 루틴이 사라진다. **이 부분은 반드시 고쳐야 한다**(Step 5).

## 결정 확정 (2026-08-19)

사용자 답변으로 확정된 사항. 재논의하지 않는다.

| 질문               | 확정                                                                       |
| ------------------ | -------------------------------------------------------------------------- |
| Q1 기존 섹션       | **선반·리포트 → 스캔 탭, 기록 → 루틴 탭.** 내 고민 탭은 고민 흐름만 담는다 |

| Q5 고민 집중 케어  | **기존 `Routine.condition` 필드 활용.** 모델·프롬프트 변경 0               |
| Q4 제품 추천       | **미정** — Step 0 실측(성분명 검색) 결과를 보고 정한다                     |

**Q3 에 따라 반드시 함께 넣는 것:**

- 프롬프트에 **"확신이 없으면 넣지 말 것"** 규칙(기존 프롬프트 3종과 같은 규율).
- 화면에 **"의학적 조언이 아닙니다"** 고정 문구. 성분 추천은 정보 제공이다.

**Q2 에 따라 생기는 과제:**

- `products` 를 **담긴 횟수 순으로 집계**하는 조회가 필요하다(`shelf_items` 를 세면 된다).
- 카탈로그가 비었을 때 보여 줄 시드 카드는 **성분이 없다.** 그 카드를 눌렀을 때의 동작을
  Step 2 에서 정한다(누를 때 AI 조회 / 담기만 허용 / 비활성).

## 구현 순서

- **Step 0** — 선행 실측 1건: **성분명으로 화해 검색이 되는가**(Q4-A 전제).
  안 되면 Q4 는 옵션 B 단독으로 확정한다.
- **Step 1** — 탭 재배치. `/profile` → `/concern` 경로 이동, 이름 "내 고민", 순서 교체.
  _화면 내용은 그대로 옮기기만 한다(리다이렉트 포함). 여기서 기능을 바꾸지 않는다._
- **Step 2** — 인기제품 카드 통일 + 상세 모달(Q2 결과 반영).
- **Step 3** — 고민 등록 → **성분 추천**(신규 AI). 결과를 화면에.
- **Step 4** — 성분 → **제품 추천** + 선반 담기(Q4 결과 반영).
- **Step 5** — 루틴 분화. **먼저 `saveRoutines` 의 통째 교체를 고친다**(고민 루틴이 기본 루틴에
  지워지지 않게). 그다음 목록을 기본/고민 집중으로 나눠 표시.
- **Step 6** — Q1 에 따른 섹션 이동(선반·리포트·기록) 및 잔여 정리.

## 검증

- `npm run check` · `npm run build` 통과 — **신규 라우트가 생기므로 `next typegen` 선행 필수**
- `ai-contract-check` — 새 프롬프트 2종(고민→성분, 성분→제품)의 출력 스키마 대조 + 런타임 검증
- 탭 이동 후 **옛 경로(`/profile`)로 들어온 사용자**가 깨지지 않는지(리다이렉트)
- **루틴 부분 저장** — 고민 루틴을 만든 뒤 기본 루틴을 다시 만들어도 고민 루틴이 남는지
- 빈 상태: 고민을 등록하지 않은 사용자가 "내 고민" 탭에서 막다른 길에 빠지지 않는지
- DB 를 끈 상태에서 새 화면들이 **에러 문구**를 보여 주는지(빈 상태로 위장되면 실패)

## 비범위 (Out of Scope)

- **의학적 진단·처방** — 성분 추천은 정보 제공이다. 화면에 그 문구를 고정한다.
- **고민 여러 개 동시 관리** — 이번엔 고민 1개(현재 `SkinProfile.wonder` 구조 유지).
  여러 개는 모델 변경이 필요해 별도로 다룬다.
- **인기 제품 순위 알고리즘** — Q2 에서 C 를 고르면 "담긴 횟수" 단순 집계까지만.
- **가격 표시** — 실측에서 재현되지 않아 이미 제외하기로 결정했다(2026-08-18).
