# 클라우드 OCR 연동 — 카메라 성분 인식 정확도 개선

> ⏳ **결정 대기(2026-08-13)** — Q1~Q4 확정 전에는 코드를 건드리지 않는다.
> Q1(제공자)·Q2(프록시 위치)는 나머지 전부에 영향을 주므로 **먼저** 답해야 한다.

## Context

`/testCamera` 화면에 tesseract.js 기반 OCR을 붙였으나(커밋 전, 워킹 트리),
화장품 성분표 인식률이 실사용 불가 수준이다.

이미 적용한 개선 — ROI 크롭, 3배 업스케일, `PSM.SINGLE_BLOCK`, 그레이스케일,
2560×1440 요청, worker 재사용 — 으로도 한계가 명확하다. 원인은 튜닝이 아니라 엔진이다:

- Tesseract는 LSTM 기반이지만 한국어 traineddata의 실사진 성능이 낮다.
- 화장품 성분표는 최악 조건 — 작은 글씨 + 저대비 + **곡면(원기둥 용기)** + 조명 불균일.
- 곡면 왜곡은 전처리로 못 편다. 원근/곡면 보정을 직접 구현하는 건 이 프로젝트 범위 밖이다.

사용자 목표는 "갤럭시 서클 투 서치 수준". 그건 클라우드 ML 모델이고,
클라이언트 사이드 OCR로는 도달할 수 없다. **엔진 교체가 유일한 경로다.**

관련: [../../../src/app/testCamera/page.tsx](../../../src/app/testCamera/page.tsx)

## 결정 필요 사항

### Q1. OCR 제공자

- **옵션 A: 네이버 CLOVA OCR (NCP)**
  - 장점: 한국어 최상급. 곡면·기울기·저대비에 강함. `General OCR`이 성분표 같은
    자유 양식 텍스트에 적합하고, 필요하면 `Template OCR`로 필드 추출까지 가능.
  - 단점: NCP 가입 + 결제수단 등록 + 도메인 생성 필요(콘솔 작업 10~20분).
    무료 티어가 제한적이라 해커톤 중 호출량 관리 필요.
- **옵션 B: Google Cloud Vision `DOCUMENT_TEXT_DETECTION`**
  - 장점: 가입/키 발급이 가장 빠름. 한국어도 충분히 좋음. 월 1,000건 무료.
  - 단점: 한국어 세부 정확도는 CLOVA보다 낮다는 평가가 일반적.
- **옵션 C: Upstage Document AI**
  - 장점: 한국어 특화, 국내 서비스, 문서 파싱 강함.
  - 단점: 레퍼런스가 상대적으로 적음.
- **추천: A(CLOVA).** 한국어 + 곡면 라벨이라는 조건이 정확히 CLOVA의 강점 구간이다.
  단, NCP 콘솔 셋업이 막히면 **B로 즉시 우회** — 인터페이스를 같게 설계해 교체 비용을 0에 가깝게 둔다.

### Q2. 시크릿을 어디서 들 것인가 (프록시 위치)

CLOVA/Vision 모두 **시크릿 키를 브라우저에 노출하면 안 된다.** 반드시 서버 경유.

- **옵션 A: Spring 백엔드(`animal-league-04-back`)에 엔드포인트 추가**
  - 장점: 팀 컨벤션대로 외부 연동은 백엔드 소유. 이미지 저장·재분석·과금 로깅 확장 용이.
  - 단점: 백엔드 담당자 작업이 선행돼야 함 → **FE가 블로킹된다.** 해커톤에서 치명적.
- **옵션 B: Next Route Handler `src/app/api/ocr/route.ts`**
  - 장점: 프론트만으로 완결. 즉시 착수 가능. 파일 기반 라우트가 `rewrites`보다 먼저
    평가되므로([next.config.ts:50](../../../next.config.ts)) `BACKEND_ORIGIN`과 충돌하지 않는다.
  - 단점: 시크릿이 프론트 배포 환경에도 필요. 나중에 백엔드로 옮기면 이중 작업.
- **추천: B.** 해커톤 속도가 우선이고, 클라이언트 코드는 `/api/ocr` 만 바라보므로
  나중에 A로 옮겨도 **프론트 변경은 rewrite 한 줄**이다. 되돌리기 비용이 낮은 쪽을 먼저 간다.

### Q3. tesseract.js를 남길 것인가

- **옵션 A: 완전 제거** — 의존성·번들·언어 데이터(수 MB CDN 다운로드) 모두 사라짐.
- **옵션 B: 폴백으로 유지** — 네트워크 실패/할당량 초과 시 대체.
- **추천: A(제거).** 폴백이 실사용 불가 수준의 결과를 내놓으면 폴백이 아니라 오답이다.
  실패는 실패라고 표시하는 편이 낫다. 남길 이유가 생기면 그때 되살린다.

### Q4. 이미지 전송 형식·용량

- ROI 크롭 결과를 `canvas.toBlob("image/jpeg", quality)` 로 보낸다. base64 대비 33% 작다.
- **결정 필요**: 품질/최대 변 길이. CLOVA는 큰 이미지를 받지만 업로드 시간이 체감된다.
- **추천**: 최대 변 2048px, JPEG q=0.9. 모바일 LTE 기준 ~300KB, 1초 내 업로드.
  현재의 3배 업스케일은 **제거한다** — 클라우드 OCR은 원본 해상도를 선호하고
  업스케일은 파일만 키운다(Tesseract 전용 최적화였다).

## 구현 순서

- **Step 0**: Q1~Q4 확정. NCP/GCP 콘솔에서 키 발급 (사용자 작업).
- **Step 1**: `src/lib/env.ts` + `.env.example`에 키 추가. `.env.local`은 사용자가 직접 채운다.
- **Step 2**: `src/app/api/ocr/route.ts` — 이미지 수신 → 제공자 호출 → `{ text }` 반환.
  이 시점에 `curl`로 단독 검증 가능(고정 샘플 이미지 파일 사용).
- **Step 3**: `src/api/ocr.ts` 래퍼. `api.post` 사용, 실패 시 `ApiError`.
- **Step 4**: `page.tsx`에서 tesseract 제거하고 교체. ROI 크롭·가이드 박스는 그대로 재사용.
- **Step 5**: `tesseract.js` 의존성 제거, 정리.

각 Step은 독립 커밋 가능하다. Step 2까지만 해도 백엔드 없이 정확도를 실측할 수 있다.

## 검증

- `npm run check` 통과 (타입 + 린트 + 포맷)
- `npm run build` 통과
- 서버/클라이언트 경계 — `route.ts`는 서버 전용, 시크릿이 `page.tsx`로 새지 않는지 확인.
  `npm run build` 후 `.next/static`에서 키 문자열이 검색되지 않아야 한다.
- 수동 확인: `/` → "카메라 테스트" 버튼 → `/testCamera` → 가이드 박스에 성분표를 담고 "인식하기".
  DevTools Network에서 `POST /api/ocr` 의 요청 크기(<500KB)와 응답 텍스트를 확인.
- **정확도 비교**: 동일한 화장품 3종을 tesseract 결과와 나란히 비교해 기록에 남긴다.
  "좋아진 것 같다"가 아니라 실제 문자열로 판단한다.
- ⚠️ 백엔드 레포가 로컬에 없어 `backend-dto-check` 대조 불가.
  Q2에서 A(Spring)를 택하면 그때 대조가 필수 선행 작업이 된다.

## 비범위 (Out of Scope)

- **원기둥 용기 전체 성분 스캔** (사용자가 후순위로 지정). 여러 장을 이어붙이는
  파노라마/스티칭은 별도 작업이다. 우선 한 장 인식 품질부터 확보한다.
- 인식된 성분 텍스트의 **파싱·성분 DB 매칭**. 이번엔 원문 텍스트 출력까지만.
- 가이드 박스 **드래그 리사이즈**. 고정 박스로 충분한지 먼저 확인한 뒤 판단.
- OCR 결과 캐싱·이미지 저장.
